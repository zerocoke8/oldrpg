# 세계

지역의 타일·씨앗·플래그 선언·적 배치·지역 간 문. 서버가 부팅에서 읽어 검증하고
(`server/content/world.ts`) 엔진에 주입한다 — `engine/` 은 파일을 읽지 않는다.

## 이것은 밸런스와 다르다

`content/balance/` 의 수치는 **바꿔도 공짜다.** 여기 있는 것은 아니다.

**씨앗을 한 글자 고치면 `seed_id` 가 바뀐다.** `state_hash` 가 달라지므로 그 방의
생성된 텍스트가 전부 캐시 미스가 되고, 다음 입장에서 LLM 을 다시 부른다.
`sensitive` 를 하나 늘리면 그 방이 가질 수 있는 상태가 2배가 된다.

그래서 형식만 JSON 이고 **취급은 코드와 같다** — 고칠 때는 리뷰를 거친다
(CLAUDE.md 의 "무엇이 코드고 무엇이 데이터인가").

되돌리면 원래대로 돌아온다. `seed_id` 가 카운터가 아니라 씨앗 내용의 해시라
A → B → A 로 되돌리면 옛 텍스트가 그대로 복구된다.

## 파일

```
world.json          스폰 + 플래그 선언. 지역이 아닌 것들이 여기 온다
regions/<id>.json   지역 하나. 파일 이름이 곧 지역 id 다
```

### `world.json`

```json
{
  "spawn": { "region": "d6", "x": 2, "y": 1 },
  "flags": {
    "journal_recovered": { "default": "false", "broadcast": true }
  }
}
```

`flags` 는 **이 세계에 존재하는 모든 월드 플래그의 선언**이다. 값을 바꾸는 것은
엔진(전투 승리 등)이고, 여기 없는 플래그를 켜려 하면 부팅이나 런타임이 거절한다.

- `default` 는 JSON 스칼라의 문자열 표기 (`"false"`, `"0"`, `"\"x\""`).
  `state_hash` 는 이 문자열을 그대로 해시하므로 `"false"` 와 `"0"` 은 다른 상태다.
- `broadcast: true` 면 값이 `snapshot.world` 와 `world.flag` 로 나간다.
  **공개는 옵트인이다** — 플래그는 쉽게 스포일러가 된다(`secret_door_found` 같은 것).
  꺼두면 클라이언트에 아예 가지 않는다.

`id` 를 JSON 안에 다시 적지 않는다. 두 군데 적으면 어긋날 수 있고, 그건 사람이
눈으로 못 잡는 종류의 오류다 (`content/balance/` 의 키와 같은 규칙).

## 지역 하나

| 필드 | | |
|---|---|---|
| `name` | 표시 이름 | 상태창에 나온다. id 가 아니다 |
| `tiles` | 한 줄이 y, 한 글자가 x | 모든 줄의 길이가 같아야 한다 |
| `seeds` | `"x,y"` → 씨앗 | 걷는 칸에는 **전부** 있어야 한다 |
| `sensitive` | `"x,y"` → 플래그 이름들 | 반응할 플래그만 좁게. 상한 4개 |
| `enemies` | `"x,y"` → 적 id | `'E'` 타일과 짝이 맞아야 한다 |
| `npcs` | id → NPC | 아래 참조 |
| `exits` | 지역 밖으로 나가는 문 | 아래 참조 |

타일 글자: `#` 벽 · `.` 통로 · `S` 시작 · `T` 보물 · `E` 적

적의 **수치**는 여기 없다 — `content/balance/enemies.json` 이 소유한다.
여기 있는 것은 '어디에 있는가' 뿐이라, 같은 적을 여러 지역에 둘 수 있다.

### 지역 크기

**50방쯤으로 유지한다.** 지역 하나가 세 가지의 단위를 겸하기 때문이다:
관심영역(`canSee` 가 지역 동일성이다), 서버측 안개(스냅샷이 한 지역만 싣는다),
진행(문을 플래그로 잠근다). 1000방을 한 지역에 넣으면 셋이 한꺼번에 무너진다.

### NPC (`npcs`)

```json
"altar_keeper": {
  "at": "3,1",
  "name": "제단지기",
  "persona": "무너진 서고의 제단을 지키는 늙은 사제. 눈이 어둡고 말수가 적다...",
  "sensitive": ["guardian_slain"],
  "topics": [
    { "id": "greet",  "label": null,           "seed": "낯선 이를 흘깃 보고는...", "requires": null },
    { "id": "warden", "label": "파수꾼에 대해", "seed": "남쪽 홀을 지키는...",     "requires": null }
  ]
}
```

**NPC 가 전역 목록이 아니라 지역 파일 안에 있는 이유**: NPC 는 방에 서 있고
방은 지역에 있다. 전역 목록으로 두면 `roomId` 를 `"b1:3,1"` 같은 문자열로
적게 되고, 그 문자열이 지역과 어긋나도 아무도 모른다 — 실제로 부팅이
`FOREIGN KEY constraint failed` 로 죽은 적이 있고, 그 메시지에는 어느 NPC 가
어느 방을 못 찾았는지가 없다. 지역 안에 두면 좌표만 적으면 되고, 그 좌표가
그 지역의 걷는 칸인지는 같은 파일을 보는 검증기가 바로 안다.

- **키가 곧 NPC id 다.** 지역을 넘어 **전역 유일**해야 하고(`npcs` 표의 PK),
  `:` 를 쓸 수 없다 (승급 큐 키의 구분자다).
- `at` 은 그 지역의 **걷는 칸**이어야 한다.
- `persona` 는 그 사람의 목소리이고 모든 주제에 함께 들어간다. `topic.seed` 는
  그 주제에 대해 무엇을 아는가. **둘을 합친 것이 `seed_id` 다** — 하나만
  고쳐도 그 NPC 의 대사가 전부 캐시 미스가 된다.
- `topics` 는 **배열이다.** 순서가 곧 대화 메뉴의 순서라서 — 이 저장소에서
  키가 id 가 아닌 유일한 곳이다.
- `requires` 가 있는 주제는 그 플래그가 켜져야 목록에 나타난다. 잠긴 주제는
  클라이언트에 **아예 가지 않는다** (스포일러가 되므로).
- `"guild": true` 인 NPC 에게만 승급을 신청할 수 있다. 없으면 `false` 다 —
  같은 방에 서 있어도 접수를 받지 않는다.

### 문 (`exits`)

```json
{ "at": "5,5", "dir": "east", "to": { "region": "b2", "x": 1, "y": 3 },
  "requires": "guardian_slain", "minRank": 2, "oneWay": false }
```

- **`dir` 쪽은 반드시 벽이어야 한다.** 걸어갈 수 있는 칸을 가리키면 같은 키
  입력에 두 가지 뜻이 생긴다 — 한 칸 이동인가 지역 이동인가.
- `requires` 가 `null` 이 아니면 그 플래그가 켜져야 열린다. 플래그는
  `world.json` 의 `flags` 에 선언돼 있어야 한다.
- `minRank` 는 **그 사람의 자격**이다 (기본 `0` = 아무나). `requires` 와는
  묻는 것이 다르다 — `requires` 는 "세계가 열렸는가", `minRank` 는 "당신이
  자격이 있는가". 그래서 둘을 함께 걸 수 있고, 플래그가 먼저 검사된다.
  숫자는 `content/balance/ranks.json` 의 등급 번호다.
- `oneWay: false` 면 **반대편에 짝이 있어야 한다.** 없으면 들어갔다 못 나온다.

**벽·봉인·등급은 와이어에서 전부 같은 `ack{blocked}` 다.** 구별할 수 있으면
사방으로 밀어 보는 것만으로 숨긴 문을 찾아낸다. 차이는 문장에만 있고, 등급만
예외로 **무엇이 필요한지 이름을 말해 준다** — 자격은 감출 이유가 없고, 감추면
플레이어가 할 일을 알 수 없다.

## `missions.json` — 임무

지역 파일이 아니라 최상위에 있는 이유: 게시하는 사람(마을의 접수원)과 목표(괴담의
적)가 **다른 지역에 있다.** 지역 파일에 넣으면 어느 쪽에 적어야 하는지가 매번 갈린다.

```json
"m_containment": {
  "npcId": "registrar",
  "name": "격리 구역 정리",
  "brief": "격리 구역의 창백한 접목을 셋 지울 것.",
  "minRank": 1,
  "requires": "journal_recovered",
  "goal": { "kind": "slay", "enemyId": "pale_grafting", "count": 3 },
  "reward": [{ "itemId": "dark_shard", "qty": 1 }]
}
```

- **키가 곧 임무 id 다.** `player_missions` 에 그 문자열이 들어간다.
- `npcId` 는 **`"guild": true` 인 NPC** 여야 한다. 아니면 말을 걸어도 목록이
  비어 있고, 왜 안 보이는지가 어디에도 안 적힌다 (부팅이 거절한다).
- `requires` 와 `minRank` 는 문의 그것과 같은 한 쌍이다 — "세계가 내걸었는가"
  와 "당신이 자격이 있는가". **게시를 먼저 본다.** 아직 안 걸린 임무 앞에서
  "등급이 모자라다" 고 답하면 그 임무의 존재를 자백하는 셈이다.
- 게시 안 된 임무는 목록에 **아예 가지 않고**, id 로 찔러도 "없는 임무" 와
  같은 문장으로 답한다. 구별할 수 있으면 id 를 넣어 보는 것만으로 앞으로
  나올 임무를 전부 알아낼 수 있다.
- `goal.kind` 는 `slay` 뿐이다. 종류를 늘리면 데이터가 조건식을 갖게 되고
  그건 스크립트 언어다.
- `reward` 는 **아이템만** 준다. 등급은 여전히 접수원에게 따로 신청한다 —
  두 계통을 직교로 두어야 `ranks.json` 이 임무 목록에 종속되지 않는다.
- 목표가 되는 적은 **어느 지역엔가 배치돼 있어야 한다.** 정의만 있고 아무 데도
  없으면 그 임무는 영영 0/1 이고, 증상이 '아무 일도 안 일어남' 이라 눈으로
  못 잡는다 (부팅이 거절한다).

진행은 **전리품과 같은 목록**으로 오른다 — 피해를 준 사람 전원. 막타 기준이면
"같이 잡으면 전리품은 나오는데 임무는 안 오른다" 가 되고, 그건 함께 싸울 이유를 깎는다.

### `count` 를 정하기 전에 돌려 볼 것

`npm run sim` 의 **임무 완주** 표가 `count` 마릿수를 연달아 싸워 본다. 한 판
승률만 보면 안 된다 — 승률 100% 인 적도 한 판에 체력을 60% 가져가면 둘을
연달아 잡는 임무는 회복 없이 두 번째에서 죽는다. 실제로 그렇게 썼다가 걸렸다.

`test/balance.ts` 가 두 가지를 강제한다: 게시되는 모든 임무는 **스킬과 물약이면
끝낼 수 있어야** 하고(60% 이상), 그중 하나는 **기본 공격과 빈손으로도** 끝낼 수
있어야 한다 — 처음 받는 일이라 거기서 죽으면 그게 첫인상이다.

## 검증

부팅에서 두 겹으로 본다. 틀리면 **서버가 뜨지 않는다.**

| 어디서 | 무엇을 |
|---|---|
| `server/content/world.ts` | 한 파일 안에서 판정되는 것 — 모양, 좌표 키 형식, 타일 글자, 줄 길이, 모르는 필드 |
| `server/db/seed.ts` 의 `assertWorldData` | 파일을 넘나드는 것 — 씨앗 누락, `'E'` ↔ `enemies` 짝, 적·플래그가 실재하는가, 문의 짝, NPC 의 방·플래그·주제, 스폰 |

## 새 지역 만들기

```
npm run author -- b3 --dry-run    # 지도만 그려 본다. 모델을 부르지 않는다
npm run author -- b3              # 개요 + 씨앗을 만들어 regions/b3.json 에 쓴다
```

`content/world/briefs/README.md` 에 순서와 필드가 있다.

**이미 있는 것은 도구가 절대 덮어쓰지 않는다** (규칙 3). 빈 것만 채운다.
