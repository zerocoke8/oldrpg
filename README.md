# oldrpg — LLM 텍스트 머드

웹 브라우저에서 돌아가는 멀티플레이어 텍스트 머드. 세계의 묘사·NPC 대사·퀘스트를
LLM이 생성하지만, 게임 규칙과 상태는 전부 결정론적 코드가 소유한다.

설계 원칙과 로드맵은 [CLAUDE.md](./CLAUDE.md) 에 있다. 이 문서는 **지금 무엇이 만들어져
있고, 무엇이 왜 미뤄졌는가** 를 적는다.

---

## 현재: 로드맵 5단계 전부 완료

1단계(서버 권위 이동 + WebSocket 동기화), 2단계(씨앗 → LLM → DB 고정, 좌표 락,
`state_hash` 캐시, 실패 시 폴백), 3단계(플래그, 영향 범위, 백그라운드 워커),
4a단계(실시간 전투), 4b단계(NPC 대사), 5단계(JRPG 커맨드 창 · 미니맵 · 모바일
터치)가 끝났다.

로드맵의 4단계는 "NPC와 전투" 둘이라 **4a(전투) / 4b(NPC 대사)** 로 쪼갰다.
단계를 건너뛴 것이 아니라 나눈 것이다.

```bash
npm install
cp .env.example .env   # ANTHROPIC_API_KEY 를 채운다 (없어도 돌아간다)
npm run dev            # 서버(8787) + 클라이언트(5173)
```

**키가 없으면** 서버는 결정론적 폴백 문장만 쓰고 나머지는 똑같이 돈다.
부팅 로그가 어느 쪽인지 알려준다.

브라우저 탭 두 개를 연다:

- <http://localhost:5173/?as=a>
- <http://localhost:5173/?as=b>

토큰이 `localStorage["mud.token.a"]` / `["mud.token.b"]` 로 갈리므로 **같은 브라우저의
탭 두 개여도 서로 다른 캐릭터**다. 화살표로 이동, Enter로 살펴보기.

확인할 수 있는 것:

- 한쪽이 움직이면 다른 쪽 **미니맵의 점이 따라 움직인다**
- 같은 방에 들어가면 **"○○ 님이 서쪽에서 들어왔다."** 가 뜬다
- 벽에 부딪히면 문장만 뜨고 위치는 그대로다 (서버가 판정한다)
- **새로고침해도 상대 화면은 조용하다** (유예 8초). 좌표·안개도 복원된다
- 남서쪽 끝(`E` 타일)에 **그림자 파수꾼**이 있다. **공격을 한 번 누르면 계속
  주고받는다** — 지켜보다 스킬을 누르면 다음 호흡에 기본공격 대신 나간다
- 처음 가는 방은 **폴백 문장이 즉시** 뜨고, 잠시 뒤 **그 줄이 조용히 교체**되며
  "새로 생성됨" 뱃지가 켜진다 (규칙 4). 두 번째 방문부터는 처음부터 확정본이다

세계를 바꿔 보려면 (`MUD_DEV=1 npm run dev:server` 로 띄운 뒤 서버 콘솔에):

```
flag guardian_slain true
```

- 영향권에 서 있으면 **"주변의 공기가 달라졌다"**, 밖이면 **"멀리서 무언가 무너지는 소리"**
- **서 있는 화면은 그대로다.** 새 묘사는 다시 들어가거나 살펴볼 때 나온다
- 상태창에 "파수꾼 처치됨" 이 뜬다. 되돌리면 옛 묘사가 그대로 복구된다

## 구조

```
shared/      두 쪽이 함께 import 하는 계약. 타입과 '런타임 검증기'가 같이 산다
server/
  engine/    맵·이동·플래그. 진실을 계산한다. narration/ db/ net/ 을 import 하지 않는다
  narration/ LLM 호출 · 프롬프트(파일) · 큐. DB 핸들을 잡지 않는다
  world/     engine + db + narration + net 을 조합하는 유일한 곳
             roomText.ts(플레이어 경로) / upgrade.ts(승급)
             events.ts(세계 변화) / combat.ts(실시간 스케줄러)
  db/        모든 SQL 이 queries.ts 한 파일에 있다 (나중에 Postgres 로 옮기려고)
  net/       세션·유예·presence 팬아웃·핸들러
client/
  net/       소켓 재접속, 재조정(reconcile)
  input/     키보드 / 자유 텍스트 -> Action 어댑터
  ui/        미니맵 · 로그 · 상태 · D패드
```

### 규칙 1·2 는 주석이 아니라 빌드 에러다

CLAUDE.md 110줄("`engine/`이 `narration/`을 import 하는 코드가 생기면 규칙 1이 깨진 것이다")은
`.eslintrc.cjs` 의 `no-restricted-imports` 로 강제된다. 다음은 전부 **린트 에러**다:

| 금지 | 이유 |
|---|---|
| `engine/` → `server/narration/` | 엔진이 진실, LLM은 묘사만 한다 |
| `engine/` → `db/`, `better-sqlite3` | 엔진은 영속화를 모른다. 상태 변경은 반환값(effects)으로 낸다 |
| `engine/` 에서 `Math.random()` | 엔진은 결정론이어야 한다. 난수는 주입받는다 |
| `narration/` → `db/` | **LLM 출력이 상태를 바꾸는 경로가 생긴다** |
| `narration/` → `engine/` | 얼어붙은 `RoomTextRequest` 만 받는다 |
| `client/` → `@anthropic-ai/*` | 클라이언트는 LLM을 호출하지 않는다 (규칙 2) |
| `engine/` → `@anthropic-ai/*` | 규칙 1 의 가장 직접적인 위반 — 엔진이 모델을 직접 부르는 것 |
| `shared/` → `@anthropic-ai/*` | **클라이언트가 `shared/` 를 런타임으로 import 한다** — SDK 가 브라우저 번들로 샌다 |
| `shared/` → `server/`, `client/`, `better-sqlite3`, `ws` | `shared/` 는 계약만 산다. 화살표는 언제나 양쪽 → `shared/` 한 방향이다 |

`shared/narration.ts` 의 **계약 타입**은 예외적으로 허용된다 — 구현이 아니라 서명이다.

두 가지를 덧붙여 둔다.

**강제는 부르는 사람이 있어야 강제다.** 이 표가 오래 '선언' 이었다 — `npm run lint` 가
정의되어 있었지만 그것을 부르는 자동 경로가 없었다(`build` 는 `tsc --noEmit && vite build`
뿐이다). 지금은 `test:all` 이 `lint && typecheck` 로 시작한다. 그 전에는 `engine/` 이
SDK 를 직접 import 해도, `shared/` 가 SDK 를 끌어들여 브라우저 번들로 새어도 lint·tsc·
vite build 가 전부 초록이었다 — 일부러 위반해서 확인한 사실이다.

**오버라이드에 `no-restricted-syntax` 를 넣지 말 것.** eslint 8 은 같은 키의 규칙을
병합하지 않고 **교체**한다. 어느 오버라이드에든 그 키를 넣는 순간 그 디렉터리에서
위 표의 `Math.random()` 금지가 조용히 사라지고, 4a 전투의 시드 재현성이 거기 걸려 있다.
(동적 `import()` 를 막고 싶은 유혹이 정확히 이 함정으로 이어진다. 저장소에 `import()`
사용이 0건이라 얻을 것도 없다.)

### 테스트는 실물 API 로부터 격리돼 있다

`boot()` 에 `llm: "off"` 가 있고 모든 스위트가 그것을 쓴다 (환경변수 `MUD_NO_LLM=1`
도 같은 뜻이다). 그 전에는 **렌더러를 '안 꽂은 것' 이 곧 '네트워크로 나가는 것'** 이었다 —
테스트는 방·NPC 두 렌더러 중 필요한 쪽만 꽂는 것이 자연스러운데, 안 꽂은 쪽은
`.env` 에 키가 있는 기계에서 실물 API 로 나갔다. 여섯 중 넷이 한쪽을 빠뜨리고 있었고,
`test:all` 이 실물 호출 38회를 내보내며 `test:npc` 가 46/46 → 43/46 으로 깨졌다.

```
                 이전                    지금
키 없는 기계     초록                    초록
키 있는 기계     빨강 (실물 호출 38회)   초록 (실물 호출 0회)
```

키 있는 기계만 빨간데 그 빨강이 진짜 회귀가 아니면, 사람은 빨강을 무시하는 법을
배운다. **기본값이 위험한 쪽이면 안 된다.**

부팅 로그도 두 렌더러를 따로 찍는다 — 한 줄로 방 렌더러만 보고 말하면 NPC 렌더러가
실물인 채로 "주입된 렌더러" 라고 말하는 거짓말이 된다. 실제로 그랬다.

```
[mud] 서술: 방=폴백 · NPC=폴백 · 실물 모델 호출 꺼짐 (llm:"off" / MUD_NO_LLM=1)
[mud] 서술: 방=claude-opus-5 · NPC=claude-opus-5 · 백그라운드 승급
```

격리하고 나니 실물 `makeLlmNpcRenderer` 와 `loadNpcPrompt` 를 '우연히' 태우던 유일한
경로가 사라졌다. 그래서 방 렌더러에 해 두었던 스텁 검증을 NPC 쪽에도 세웠다
(`test/pipeline.ts` ⑧′).

## 프로토콜 (17종)

`shared/protocol.ts` 하나가 계약 전부다. 세 가지 불변식 위에 서 있다:

1. **화면에 문장을 올리는 메시지는 `log` 하나뿐이다.** `ack`·`presence.*`·`room.*` 는
   구조화 데이터만 싣는다. 클라이언트는 문장을 조립하지 않는다 — 벽 부딪힘도,
   "○○ 님이 들어왔다"도. 그래서 2·3단계가 **클라이언트 배포 없이** 서버 안에서 끝난다.
2. **`state_hash` 는 와이어에 절대 나타나지 않는다.** 클라이언트는 캐시 키를 들지 않는다.
3. **클라이언트는 모르는 것을 무시하거나 격하한다** — 모르는 필드, 모르는 `t`,
   모르는 enum *값*(`kind`→`narr`, `source`→`fallback`). `never` 기반 exhaustive switch를
   쓰지 않는다. 그래서 2·3단계의 추가분 대부분이 비파괴적 변경이 된다.

| 클라 → 서버 (3) | 서버 → 클라 (14) |
|---|---|
| `hello` `action` `pong` | `welcome` `snapshot` `ack` `room.describe` `self.patch` |
| 액션 5종: `move` `look` `say` `unparsed` `resync` | `presence.join/move/leave` `room.enter/leave` |
| | `log` `log.replace` `ping` `error` |

### 두 계열을 나눈 이유

- **`presence.*` = 미니맵 피드.** 나를 볼 수 있는 모두에게. 손실 허용 — 규모에서
  throttle·coarsen·withhold 된다.
- **`room.*` = 서사 피드.** 그 방의 재실자에게만. 무손실, 절대 coarsen 안 함.

하나로 합쳐 뒀다면, 팬아웃이 아파져서 presence를 5Hz로 throttle 하는 날
`"○○이 들어왔다"` 가 **조용히 삼켜진다**.

방출 순서 규칙: `presence.*` 를 `room.*` 보다 먼저 보낸다 — 로그에 "사라졌다"가 찍히는
순간 미니맵의 점은 이미 옮겨져 있어야 한다.

### 재조정에 롤백 분기가 없다

`ack` 는 성공이든 거절이든 **항상** 권위 `pos` 를 싣는다. 그래서 화면 위치는 언제나
순수 함수 `replay(confirmed, pending)` 이고, `client/net/reconcile.ts` 에 `if (ok)` 분기가
존재하지 않는다.

이게 성립하려면 **액션에 귀속 가능한 모든 실패가 `ack` 로 와야** 한다
(`rate_limited` `internal` `bad_args` 포함). `error` 로 답하면 그 액션의 `pending` 엔트리가
영원히 남아 예측 위치가 한 칸 어긋난 채 복구되지 않는다. 그래서 **`error` 는 항상 연결을
끊는다** — pending 이 연결과 함께 사라지게.

## 데이터 모델

표 다섯 개: `meta` `rooms` `world_flags` `room_text` `players`.
비어 있는 자리표시자 표는 만들지 않는다.

### `state_hash` = `` `${seed_id}.${flags_decl_hash}.${valueDigest}` ``

`rooms.sensitive_flags` 에 **선언된 플래그만** 해시한다 (CLAUDE.md 44-48줄).
세 조각이 각각 하는 일:

| 바뀐 것 | 결과 |
|---|---|
| 플래그 값 (`false`→`true`) | 캐시 미스. 옛 행 생존 → **되돌리면 옛 텍스트 복구** |
| 씨앗 문자열 편집 | 캐시 미스. **씨앗을 되돌려도 옛 행 복구** (`seed_id` 가 내용 파생이라서) |
| 플래그 **선언** 추가·삭제·재정렬 | 깨끗한 미스. 옛 행이 '다른 상태'로 **오독되지 않음** |

`seed_id` 가 증가 카운터가 아니라 `sha256(seed)[0:8]` 인 것이 요점이다 — 되돌림 동작이
플래그와 씨앗에서 **일치**하고, 엔진이 DB 없이 `state_hash` 를 계산할 수 있다.

### 1단계의 하드코딩 문장은 2단계 LLM 출력이 차지할 '바로 그 행' 에 산다

`room_text` 에 `source ∈ ('fallback','llm','authored')` 한 칼럼이 있고, 1단계는 전부
`'fallback'` 이다. 2단계 전환일에 기존 행은 **전부 유효한 캐시 히트**이므로
마이그레이션도, 콜드스타트 정지도 없다. 규칙 2의 "딱 한 번"은 주석이 아니라 WHERE 절이다:

```sql
-- 최초 기록 (그리고 무조건 재조회)
INSERT INTO room_text (...) VALUES (...) ON CONFLICT (room_id, state_hash) DO NOTHING;
-- 2단계 승급 — 0행 매치 = 남이 먼저 생성했다 = 오류가 아니다
UPDATE room_text SET text=?, source='llm', ... WHERE room_id=? AND state_hash=? AND source='fallback';
```

이 보증은 **프로세스를 넘어서도** 성립한다. 뮤텍스가 못 하는 일이다.

1단계는 부팅 프리시드를 **하지 않고** 첫 입장 때 lazy 기록한다 — 프리시드하면
"조회 → 없으면 생성 → 기록" 중 조회만 실행되고 나머지가 죽은 코드가 된다.

### 규칙 4는 프로토콜 속성이다

이동 처리는 두 단계다.

- **Phase A** (`await` 없음): `ack` + `self.patch` + `room.describe` + 모든 presence/room
  이벤트 + 재실자 로스터 줄
- **Phase B** (`await roomText()` 뒤): 서술 `log{narr}` **하나뿐**. 세션별 프로미스 체인.

(a) 이동이 절대 LLM 뒤에 서지 않고 (b) 방 A의 묘사가 이미 방 B에 선 플레이어에게
도착하는 인터리브가 **구조적으로 불가능**하다.
"서술 텍스트는 이동 확정보다 늦게 도착할 수 있다" 가 **클라이언트 계약**이다.

2단계에서는 한 겹 더 있다: Phase B 가 기다리는 것도 LLM 이 아니라 폴백 렌더러다.
모델은 백그라운드 큐에만 있다 (아래 2단계 절).

## 신원과 유예

계정도 비밀번호도 없다. 서버가 32바이트 무기명 토큰을 발급하고 `sha256` 만 저장한다.
클라이언트는 `localStorage["mud.token." + (?as ?? "a")]` 에 넣는다.

**유예(linger)는 프로토콜에 보이지 않는다.** 유예 중인 플레이어는 모든 관찰자와 모든
스냅샷에게 그냥 "가만히 서 있는 플레이어"다.

- 소켓 종료 시 **아무것도 방출하지 않는다**. `byRoom`·`sessions` 에 그대로 남는다
- `room.describe.occupants` 와 `snapshot.presence` 에 **둘 다** 포함한다 — 하나만 포함하면
  둘이 어긋나 '점 없는 유령'이 생긴다
- 유예 안에 돌아오면 타이머만 취소하고 **역시 아무것도 방출하지 않는다**
- 유예(8초)가 만료돼야 비로소 `presence.leave` + `room.leave` + `log` 가 나간다

성립 조건: `presence.join`/`room.enter` 는 `player.id` 기준 **멱등 upsert**,
모르는 id 에 대한 `leave` 는 **no-op**.

### `connId` 에폭 가드

`close` 핸들러와 모든 Phase B 연속은 `connId` 를 확인한다.
**이 한 줄이 없으면 새로고침이 옛 소켓의 늦은 `close` 를 통해 '새' 세션을 지워
상대 미니맵에서 영구히 사라진다.** 두 브라우저 테스트에서 가장 먼저 만나는 버그다.

## 2단계 — 생성 파이프라인

### 규칙 4가 '구조' 다: 플레이어 경로에는 모델 호출이 없다

플레이어의 요청 경로(`world/roomText.ts`)에는 **결정론적 폴백 렌더러만** 있다.
LLM 은 백그라운드 큐(`world/upgrade.ts`)에만 존재한다. 그래서 실수로
기다리게 만들 방법이 없다 — 코드에 그 경로가 없다.

```
방 입장
 └─ 조회 ─┬─ hit(llm/authored) ──────────→ log{narr, source:'llm'}      끝
          └─ miss 또는 hit(fallback)
               ├─ 폴백 문장을 '즉시'      → log{narr, source:'fallback'} ← 플레이어는 여기서 끝
               └─ 승급 큐에 등록
                    └─ (백그라운드) LLM → UPDATE ... WHERE source='fallback'
                         └─ 재조회 → log.replace{id, text, source:'llm'} → 그 줄만 교체
```

`log.replace` 는 그 줄을 받은 **모든** 세션에 간다. 생성을 촉발한 한 명에게만
보내면 같은 방의 두 사람이 영구히 다른 문장을 보게 되고, 그건 CLAUDE.md 20줄
("그 시점부터 모든 플레이어에게 동일하다") 위반이다. 그리고 교체 문장은 우리가
방금 만든 것이 아니라 **재조회한 DB 값**이다 — 남이 먼저 확정했으면 그쪽이 진실이다.

### 좌표 락

두 겹이다.

| 층 | 무엇을 막나 |
|---|---|
| `narration/queue.ts` 의 `(roomId, stateHash)` 중복 제거 | 같은 방에 동시 진입한 두 명이 API 를 **두 번 호출**하는 것 (비용) |
| `PRIMARY KEY` + `ON CONFLICT DO NOTHING` + `UPDATE ... WHERE source='fallback'` | 두 개의 텍스트가 **기록**되는 것 (정확성). 프로세스를 넘어서도 성립한다 |

단일 프로세스로 가기로 했으므로 `room_gen_lock` 표는 여전히 없다.

### 실패

- LLM 오류·거절(`stop_reason:"refusal"`)·`max_tokens` 로 잘림·빈 응답 →
  **폴백 문장이 그대로 남는다.** 반쯤 만들어진 문장을 DB 에 영구 고정하지 않는다.
- 큐가 쿨다운(기본 60초)을 걸고, 3회 실패하면 그 (방, 상태)는 포기한다.
  계속 실패하는 방이 큐를 점유하지 않는다.
- 승급이 안 된 행은 언제든 `SELECT ... WHERE source='fallback'` 로 다시 찾을 수 있다
  (인덱스 있음). 그래서 재시도 큐를 영속화할 필요가 없다.

### 프롬프트는 파일이다

```
server/narration/prompts/
  room.v1.ko.md              # '# system' / '# user' 두 절. {{seed}} {{mood}} 치환
  moods/guardian_slain.md    # '# prompt'(LLM 지시) / '# fallback'(결정론 문장)
```

**파일명이 곧 `prompt_version`** 이고 `room_text.prompt_version` 에 기록된다.
문구를 바꿀 때는 같은 파일을 고치지 말고 `room.v2.ko.md` 를 새로 만들 것 —
같은 파일을 고치면 옛 텍스트가 어느 프롬프트로 만들어졌는지 잃는다.

### 모델

기본값 `claude-opus-5`. `.env` 의 `MUD_MODEL` 로 바꿀 수 있다.
`effort: "low"` 로 부른다 — 방 묘사는 2~3문장짜리 창작이라 깊은 추론이 필요 없고,
사고를 아예 끄는 것보다 이쪽이 안전하다. 19개 방이면 전체 생성 비용은 1센트 미만이다.

## 3단계 — 이벤트 재렌더링

CLAUDE.md 의 다섯 단계를 그 순서 그대로 구현했다 (`world/events.ts`).

```
events.setFlag("guardian_slain", true)
 ├─ 1. DB 커밋 -> 메모리 갱신        (이동 경로와 같은 순서)
 ├─ 2. 미리 써둔 문장을 '즉시'       near = 영향권에 서 있는 사람
 │                                   far  = 그 밖의 사람  (파일에서 읽는다)
 │     + world.flag (구조화 상태만)
 ├─ 3. 그 플래그를 '선언한' 방만 큐에  19개 중 7개
 ├─ 4. 워커가 하나씩 재생성 -> DB     (2단계의 큐를 그대로 쓴다)
 └─ 5. 새 텍스트는 '다음 입장부터'    ← 여기서 하는 일이 '없는' 것이 이행이다
```

### 5번이 이 단계에서 가장 중요하다

CLAUDE.md 63줄: "지금 그 방에 서 있는 플레이어의 화면을 갈아치우지 않는다."

**3단계는 `log.replace` 를 절대 보내지 않는다.** `log.replace` 는 2단계의
provisional → 확정 전용이다. 플래그가 바뀌어도 서 있는 사람은 이벤트 문장
한 줄만 받고, 새 묘사는 **다시 들어가거나 직접 살펴볼 때** 나타난다.
(`look` 은 '요청' 이므로 새 텍스트를 준다 — 갈아치우지 말라는 것은
*요청하지 않은* 교체를 말한다.)

사전 생성 덕분에 그 '다음 입장' 은 폴백을 거치지 않고 **처음부터 확정본**이다.

### 승급이 진행 중인 방에서 플래그가 바뀌면

가장 미묘한 인터리브다. 그 줄은 **들어갔을 때의 상태** 묘사이므로 그 상태의
확정본으로 교체되어야 한다. 그래서 승급 워커는 플래그를 '지금의 월드' 가 아니라
**그 행의 `flags_json`(= `state_hash` 의 preimage)** 에서 읽는다.

현재 월드에서 읽으면 두 가지가 한꺼번에 깨진다 — 서 있는 사람의 줄이 새 상태
문장으로 갈아치워지고(63줄 위반), 더 조용하게는 옛 `state_hash` 로 키잉된 행에
새 플래그로 만든 텍스트가 들어가 **캐시가 오염된다** (되돌리면 엉뚱한 문장이
복구된다). 둘 다 회귀 테스트가 있다.

### 플래그 공개는 옵트인

`engine/map.ts` 의 `WORLD_FLAGS` 에서 `broadcast: true` 로 선언한 것만 와이어에
나간다. 플래그는 쉽게 스포일러가 된다(`secret_door_found` 같은 것).
표시 문구(`label`)도 **서버가** 만든다 — 클라이언트가 key 로 문장을 조립하기
시작하면 불변식 (1)의 예외가 하나 더 생긴다.

### 무엇이 플래그를 켜는가

지금은 개발용 stdin 뿐이다 (`MUD_DEV=1`, 서버 콘솔에 `flag <key> <json>`).
프로토콜 표면이 0 이라 액션 유니온에 디버그 동사가 들어가지 않았다.
**4단계 전투가 부를 진입점이 `events.setFlag()` 이고, 그 시그니처는 이미 최종형이다.**

## 4a단계 — 실시간 전투

턴제가 아니다. **공격을 한 번 누르면 자동 공격이 켜지고** 서로 계속 때린다.
지켜보다 스킬을 누르면 **다음 스윙(최대 0.5초)에 기본공격을 대신해** 나간다.

### 스케줄러

전투가 하나라도 있을 때만 도는 **게으른 100ms 루프**. 전투원마다 `nextActAt`
을 갖고, 플레이어 스윙은 500ms, 적은 900ms다.

틱을 500ms 로 두지 않은 이유: 간격이 *루프의 성질*이 아니라 *전투원의 데이터*
여야 무기 속도·가속·시전시간이 나중에 숫자 하나로 들어온다.

시각은 **단조 시계**다 (`process.hrtime`). `Date.now()` 는 역행할 수 있고,
그러면 전원이 영원히 대기하거나 한꺼번에 몰아친다 — 토큰 버킷에서 겪은 그 버그다.

### 난수

`engine/` 은 `Math.random()` 이 린트로 막혀 있다. **전투마다 시드된 PRNG를 주입**
한다. (시드 + 액션 순서)로 전투가 재현되고, 테스트가 데미지 굴림까지 결정론적이다.

### 어그로 — 누적 피해가 가장 큰 사람

`Map<playerId, 누적피해>`. 적은 매 스윙마다 argmax를 때린다. 동점은 먼저 교전한
쪽(난수 불필요). **대상이 빠지면 다시 고르고, 반드시 문장으로 알린다** —
조용히 바꾸면 남은 사람이 예고 없이 맞기 시작하고, 화면에서 이유가 사라진다.

치유·방어가 의미를 갖는 것도 이 모델 덕분이다: 딜을 많이 넣는 사람이 맞으므로
누가 맞을지가 플레이의 결과가 된다.

### 로그는 서버가 접을 것을 지정한다

평범한 타격은 `log{kind:"combat"}`, **스킬·치명타·사망·어그로 이동은 `good`/`bad`**.
클라이언트는 **연속된 `combat` 줄만** 접는다("공방이 오갔다 · 7회"). 그래서
흥미로운 사건이 접힌 덩어리를 끊고 저절로 드러난다 — 무엇을 접을지 클라이언트가
추측하지 않는다.

로그 창은 **아래에 붙어 있을 때만** 자동 스크롤한다. 0.5초마다 아래로
끌어내리면 전투 중에 로그를 읽을 수가 없다.

### 스키마 변경이 없다

| 무엇 | 어디에 |
|---|---|
| 적 정의 | 코드 (`engine/enemies.ts`) |
| 적 **사망** | `world_flags` — **`guardian_slain` 이 이미 있었다** |
| 전투 중 적 HP | 메모리 (휘발성) |
| 플레이어 HP | `players.hp` (이미 있음) |
| 전투 세션·쿨다운 | 메모리 — 접속자 표를 안 만든 것과 같은 논거 |

그래서 **파수꾼을 죽이면 3단계 파이프라인이 통째로 돈다** — 7개 방이 재생성되고,
영향권엔 "주변의 공기가 달라졌다", 밖엔 "멀리서 무언가 무너지는 소리".
단계들이 고리로 닫힌다. 회귀 테스트가 이걸 확인한다.

### 전투 문장은 결정론이다 (규칙 4)

0.5초 스윙에 모델을 기다릴 수 없다. 전투 산문은 전부 `narration/lines.ts` 다.
LLM 이 전투에 들어올 자리는 나중에 둘 — **전투 종료 후 요약**, 또는
(무기 × 적 × 결과) 키로 미리 생성해 둔 **문장 풀**(`room_text` 와 같은 패턴).
그때도 지금 문장이 폴백으로 남는다.

### 수치

플레이어 DPS ≈ 13.8/초(치명타 포함) → 200HP 는 혼자 약 15초.
적 DPS ≈ 3.9/초 → 15초면 56 피해인데 플레이어는 40HP다. **치유 없이는 진다** —
그게 실시간에서 스킬을 쓰게 만드는 긴장이다. 둘이 붙으면 절반이라 협력에 값이 붙는다.

### 적이 두 종류다 — 보스와 반복되는 적

파수꾼 하나뿐일 때는 '한 번 죽이면 끝' 인 세계였다. `guardian_slain` 이 DB 영속이라
**늦게 접속한 사람은 전투를 영영 보지 못했다.**

| | 죽음의 소유자 | 세계를 바꾸는가 | 돌아오는가 |
|---|---|---|---|
| 보스 (그림자 파수꾼) | 월드 플래그 (영속) | 켠다 → 3단계 재렌더링 | **아니오** |
| 반복되는 적 (잿빛 종잇장·녹슨 감시자) | 리스폰 대기 (메모리) | 아니오 | 45~60초 뒤 |

둘은 **배타적이다** (부팅 때 검증한다). 파수꾼이 되살아나는데 `guardian_slain` 이 켜진
채로 남으면 그 플래그를 선언한 일곱 방의 묘사가 "파수꾼이 사라진 뒤" 인 채 파수꾼과
마주 보게 되고, 플래그를 되돌리면 이번엔 지금 그 방에 서 있는 사람들의 세계가 소리
없이 뒤집힌다. 그래서 '세계를 바꾸는 적' 과 '반복되는 적' 은 아예 다른 종류로 나눈다.

리스폰 대기는 **메모리**다. 표를 만들지 않는 이유는 전투 중 HP 와 같다 — 재시작하면
전부 살아 있고 그것이 정직하다. 그리고 `setTimeout` 이 아니라 **틱이 소유한다**:
주입된 시계 위에서 돌아야 테스트가 손으로 시간을 밀 수 있고, 타이머 하나에 상태를
걸었다가 그것을 잃는 실패 모드(위의 부활 결함)를 되풀이하지 않는다.

### 돌아온 것을 어떻게 알리는가 (이 절의 유일한 설계 결정)

CLAUDE.md 63줄: **지금 그 방에 서 있는 플레이어의 화면을 갈아치우지 않는다.**
3단계가 `log.replace` 를 쓰지 않는 것과 같은 이유다. 그래서 나가는 것은 둘뿐이다:

```
log{kind:"bad"}   "잿빛 종잇장이(가) 어둠 속에서 다시 모습을 갖춘다."   ← 결정론 문장
room.describe     hasEnemy: true                                      ← 구조화 상태
```

방 묘사(`log{narr}`)도 `log.replace` 도 보내지 않는다 — 테스트가 그 둘이 오지 않는
것을 단언한다. 적이 **사라질 때**도 같은 경로로 `hasEnemy: false` 가 간다. 이걸 빼면
커맨드 창에 '싸우기' 가 남아 있다가 누르면 "여기에는 맞설 것이 없다" 는 답을 듣는다.

### 부팅에서 세계 데이터를 검증한다

`enemies.ts` 는 "맵의 'E' 타일과 짝이 맞아야 한다 (부팅 때 검증한다)" 고 적혀 있었는데
**그 검증이 없었다.** `db/seed.ts` 의 `assertWorldData()` 가 다섯 가지를 본다:

- 걷는 칸에는 전부 씨앗이 있다 (침묵 폴백 금지)
- `'E'` 타일 ↔ `ENEMIES` 가 **양방향으로** 짝이 맞는다
- 플래그를 켜는 적은 리스폰하지 않는다
- 적이 켜는 플래그는 선언돼 있다

부팅에서 죽는 편이 조용히 틀린 세계로 도는 것보다 낫다. 다섯 가지를 전부 일부러
어겨서 실제로 죽는 것을 확인했다.

그리고 이 검증이 생겼으므로 `allRooms()` 의 침묵 폴백(`SEEDS[k] ?? "특징 없는 돌 통로"`)
을 없앴다. 새 칸을 뚫고 씨앗을 빠뜨리면 아무 소리 없이 무명의 방이 하나 생기던 자리다.

### 스폰 씨앗이 맵과 어긋나 있었다

`(3,3)` 의 씨앗이 **"네 방향으로 통로가 뻗은 석조 교차로"** 였는데, `(3,2)`와 `(3,4)`가
벽이라 실제 출구는 동·서 둘뿐이다. 그리고 `(3,3)` 은 **스폰**이다 — 모든 플레이어의
첫 문장이 옆의 미니맵과 어긋났고, 위로 한 번 누르면 "단단한 벽이 앞을 막는다" 가 왔다.

씨앗은 불변이지만(규칙 3) 이건 튜닝이 아니라 엔진 데이터의 버그였다. 고치면 `seedId` 가
바뀌어 그 방만 깨끗한 캐시 미스가 된다 — `seedId` 가 내용 파생이라 되돌리면 옛 텍스트가
그대로 복구되는 성질도 그대로다 (영향 3행 미만).

19개 방의 씨앗을 전부 실제 출구와 대조했고, 어긋난 것은 이 하나뿐이었다.

### 그 밖

- **걸어 나가는 것이 곧 도망이다.** 별도의 flee 동사를 두지 않았다.
- **새로고침해도 전투가 이어진다** — 세션이 유예로 살아남으므로. 스냅샷이
  `combat` 을 싣는다.
- 유예가 만료되면 전투에서도 빠진다 (링크데드로 계속 맞다가 사라진다).
- 쓰러지면 5초 뒤 스폰에서 절반의 체력으로 일어난다. 역시 스키마 변경 없음.
  단, 그 5초짜리 메모리 타이머는 **부활의 최종 보증이 아니다** — 아래를 볼 것.

### 부활의 최종 보증은 타이머가 아니라 재개 경로다

부활을 메모리 `setTimeout` 하나에만 걸어 두면 그것을 잃는 경로가 둘 있다:

1. 프로세스가 그 5초 안에 죽는다 — `tsx watch` 재시작이 정확히 이 창이다.
2. 끊긴 뒤 3~8초 사이에 링크데드로 죽는다 — 유예 만료(8초)가 부활(사망+5초)보다
   먼저 와서 세션이 지워지고 콜백이 `!cur` 로 빠져나간다.

그러면 `hp=0` 이 DB 에 남는데, HP 를 올리는 경로가 전투 안(`mend`)에만 있고
전투는 `hp<=0` 을 거절하므로 **캐릭터가 영구히 굳는다.** 토큰을 버리는 것 말고
탈출구가 없다. 둘 다 재현되는 결함이었다.

그래서 `handleHello` 의 재개 분기가 좌표(`walkableAt`)와 **같은 자리에서** vitals 도
검사한다. 여기는 DB 가 진실인 유일한 지점이고, 타이머와 달리 유실되지 않는다.

```ts
if (!walkableAt(pos)) { pos = SPAWN; displaced = true; }   // 맵이 바뀌었다
if (hp <= 0)          { pos = SPAWN; hp = maxHp/2; revived = true; }  // 부활을 잃었다
```

**대가 하나:** 끊겼다 돌아온 사람은 5초를 마저 기다리지 않고 즉시 선다. 지연까지
재접속 너머로 보존하려면 `players.dead_until` 칼럼이 필요한데, 스키마 변경을 치를
값이 아니라고 봤다.

같은 절에서 두 번째 결함이 하나 더 나왔다 (회귀 테스트가 잡았다):
부활 타이머의 에폭 가드가 `cur.connId !== s.connId` 였는데, 유예 중인 세션을
입양하면 `cur` 과 `s` 가 **같은 객체**라서 비교가 언제나 거짓이고 가드가 통째로
죽는다. 에폭은 값으로 붙잡아야 한다 — 저장소의 다른 지연 연속들이 전부 쓰는
관용구 그대로다.

## 4b단계 — NPC 대사

방 묘사의 파이프라인을 **글자 그대로** 재사용한다. `world/npcText.ts` 는
`world/roomText.ts` 의 쌍둥이고, 승급 큐·좌표락·폴백은 하나를 공유한다.

```
npcs        id, room_id, name, persona_seed, sensitive_flags[], flags_decl_hash
npc_lines   (npc_id, topic, state_hash) PK, text, source, flags_json, model, prompt_version
```

`state_hash = seedId . flagsDeclHash . valueDigest` — 방과 같은 공식이고,
`seedId = sha256(persona + "\n" + topic.seed)[0:8]` 다. **씨앗이 둘로 나뉜다**:
`persona`(그 사람의 목소리)와 `topic.seed`(그 주제에 대해 무엇을 아는가).
둘을 함께 해시하므로 어느 쪽을 고쳐도 캐시 미스이고, 되돌리면 옛 대사가
그대로 복구된다.

### 이번이 첫 스키마 변경이다

1~4a단계는 스키마를 한 번도 바꾸지 않았다. 이제는 DB 에 **돈을 주고 만든
LLM 산출물**이 들어 있으므로, `schema.sql` 을 고쳐 다시 만드는 방식이 아니라
가산 마이그레이션(`db/migrations/002-npcs.sql`)으로 올린다. 새 DB 도 v1 을
찍고 같은 마이그레이션을 타게 해서, 두 경로가 갈라지지 않게 했다.

PK 를 `(npc_id, topic, state_hash)` 로 정한 이유: SQLite 는 PK 를 ALTER 하지
못한다. 한 NPC 가 주제별로 다른 대사를 갖고, 주제마다 상태가 다르다.

### 무엇을 물을 수 있는가도 세계의 상태다

주제는 플래그로 열린다(`requires`). 파수꾼을 쓰러뜨리면 제단지기의
**봉인된 문** 이야기가 열린다 — 4a(전투) → 3단계(플래그) → 4b(대사)가
한 줄로 이어진다.

- **잠긴 주제는 목록에 아예 없다.** "무엇을 물을 수 있는가" 자체가 스포일러다.
- **목록은 권한이 아니다.** devtools 로 `ask{topic:"sealed_door"}` 를 보내도
  서버가 `world.openTopics()` 를 다시 본다. 클라이언트가 받은 것은 안내다.
- 거절은 `ack{ok:false}` 가 아니라 **문장**이다 — 벽 부딪힘과 같은 부류로,
  계약 위반이 아니라 엔진이 계산한 세계의 진실이다.

### 방에 들어서도 말을 걸지 않는다

`room.describe` 는 NPC 의 **이름만** 싣고, 로그에 "제단지기이(가) 이곳에 있다"
한 줄이 나간다. 대사는 `talk` 을 해야 나온다. 두 가지 이유가 있다 —
지나가기만 하는 방에서 생성이 도는 것은 순수한 낭비이고(규칙 2는 비용
이야기이기도 하다), 들어서자마자 대사가 쏟아지면 방 묘사가 그 밑에 묻힌다.

### 승급이 화자를 지운 결함 (테스트가 잡았다)

`log.replace` 는 그 줄을 **통째로** 갈아치운다. 대사 줄은 `제단지기: "..."`
라는 틀을 갖는데, DB 텍스트만 그대로 밀어 넣으면 승급된 순간 화자가 사라진다.
그래서 `upgrades.watch()` 가 **그 줄을 어떻게 그렸는지**(`format` 콜백)를 함께
기억한다. 승급 서비스는 여전히 문장을 모르고, 문구는 `narration/lines.ts` 가
소유한다.

## 5단계 — UI

서버는 **한 줄도 바뀌지 않았다.** 5단계가 전부 클라이언트 안에서 끝난 것이
1단계에 정한 두 결정이 실제로 값을 했다는 증거다 — "문장을 나르는 것은 `log`
뿐" 과 "모든 입력은 같은 `Action` 으로 수렴한다".

### 화면의 역할이 셋으로 갈린다

```
로그       세계의 문장          log 만이 문장을 나른다 (불변식 1)
상태창     구조화된 지금        좌표 · HP · 적 · 월드 플래그
커맨드 창  할 수 있는 일 전부   살펴보기 · 싸우기 · 대화 · 말하기
```

전에는 '공격' 이 D패드에도 전투 패널에도 있었고, 대화 주제는 또 다른 패널에
있었다. 5단계에서 명령을 전부 커맨드 창 하나로 모았다 — 같은 명령이 두 군데
있으면 어느 쪽이 진짜인지 알 수 없고, 키보드 커서도 두 개가 된다.
`Combat` 은 적 HP 바만 남은 '상태' 가 됐고, 대화 패널은 사라졌다.

### 메뉴는 상태의 순수 함수다

`client/input/menu.ts` 는 저장된 트리를 갖지 않고 매 렌더 `UiState` 에서 다시
세운다. 그래서 적이 죽거나 NPC 의 방을 벗어나면 그 가지가 저절로 사라지고,
그 안에 서 있던 경로는 최상위로 되돌아간다. 서버가 "메뉴를 닫아라" 를 보내지
않는다 — `room.npcs` / `combat` 이라는 **구조화 사실에서 파생**된다
(4b 의 대화창이 닫히는 규칙과 같은 것이다).

권위는 여전히 서버다. 사라지지 않은 가지를 눌러도 서버가 다시 판정한다.

### 입력 어댑터가 다섯이 됐다

```
키보드 ─┐
D패드  ─┤
자유 텍스트 ─┼─> act(Action) ─> 서버
커맨드 창 ─┤
스와이프 ─┘
```

charter 79-80줄("새 입력 방식을 추가할 때는 이 객체를 만드는 어댑터만 추가한다")
그대로다. 다섯 어댑터 중 셋이 5단계에 새로 붙었는데 `handleAction` 은 한 글자도
바뀌지 않았다. `client/input/parse.ts` 는 1단계부터 있었고 부르는 곳이 없었는데,
이제 입력창이 그것을 부른다 — `북` 도 `살펴보기` 도 `말하기 안녕` 도 화살표와
같은 `Action` 이 된다. 해석하지 못한 것은 클라이언트가 판정하지 않고 그대로
서버로 가서 문장을 받는다.

### 모드가 생겼다 (charter 의 Esc 가 드디어 일한다)

```
탐색 모드    화살표=이동   Enter=살펴보기   Esc=커맨드 창 열기
커맨드 모드  화살표=커서   Enter/→=확정     Esc/←=뒤로
```

JRPG 의 필드/커맨드 구분 그대로다. 같은 키가 모드에 따라 다른 의도가 되는 것은
`client/input/keyboard.ts` 한 곳에서만 일어나고, `App` 은 키 문자열을 알지 못한다.
모드는 커맨드 창의 테두리 색과 안내 줄로 눈에 보인다 — 안 보이면 화살표가 왜
안 먹는지 알 수 없다.

`말하기` 를 고르면 입력창으로 조종이 넘어가고 메뉴는 닫힌다. 커맨드 모드로
남겨 두면 타이핑을 마치고 입력창을 나왔을 때 화살표가 여전히 커서라서, 사람은
자기가 어느 모드에 있는지 알 수 없다.

### 모바일

- 세로 화면 기준 `100dvh` 한 화면. 로그가 남는 공간을 먹고, 커맨드 창과 D패드는
  줄어들지 않는다 — 명령을 못 누르는 것보다 로그가 짧은 편이 낫다.
  360x640 부터 1280x720 까지 페이지 스크롤이 생기지 않는 것을 테스트가 잰다.
- **스와이프**: 로그 창을 쓸면 그 방향으로 한 칸. 임계값(36px)을 넘겨야 해서
  접힌 로그를 펼치는 탭과 부딪히지 않는다.
- **미니맵 탭**: 붙어 있는 칸을 누르면 그쪽으로 한 칸. 한 칸까지다 —
  여러 칸 경로를 클라이언트가 계산하기 시작하면 그것은 클라이언트가 맵을
  해석하는 것이고, 벽 판정이 두 군데 살게 된다. 벽인지도 보지 않는다.
  눌러 보고 서버가 "단단한 벽이 앞을 막는다" 고 답하는 것이 D패드와 완전히
  같은 경로다.
- D패드 46px, 입력창 글자 16px(그 아래면 iOS 사파리가 포커스할 때 확대한다),
  `env(safe-area-inset-bottom)`.

## 인벤토리 (마이그레이션 003)

첫 '표를 늘리는' 변경이다. `players` 를 한 칼럼도 건드리지 않는 순수 가산이라
기존 캐릭터도, 2·4b 단계에서 돈 주고 만든 텍스트도 그대로 살아남는다.

```
player_items   player_id, item_id, qty      PK (player_id, item_id)
```

**`players.inventory` JSON 블롭이 아닌 이유** (CLAUDE.md 의 스케치는 그쪽이었고,
그래서 헌장을 고쳤다): 수량 갱신이 한 문장으로 원자적이어야 한다.

```sql
INSERT ... ON CONFLICT (player_id, item_id) DO UPDATE SET qty = qty + excluded.qty
```

블롭이면 전부 읽고-고쳐-쓰기다. 두 명이 같은 적을 동시에 잡거나 한 사람이 두 탭에서
물약을 마시면 그 사이에 낀 갱신이 사라진다. `players.seen` 이 JSON 인 것은 괜찮다 —
통째로만 읽고 쓰며 경합이 없다.

`qty > 0` 이 CHECK 다. **0개를 가진 행은 존재하지 않는다** — 다 쓰면 행을 지운다.
그래야 "가지고 있는가" 가 행의 존재와 같은 뜻이 되고, 조회하는 모든 곳이 0을 따로
걸러낼 필요가 없다. 인덱스는 만들지 않았다: PK 의 앞자리가 `player_id` 라
"이 사람의 전부" 질의가 그 인덱스를 그대로 탄다.

### 정의는 코드, 표는 그림자 — 그리고 가방은 메모리에 없다

`server/engine/items.ts` 가 아이템을 소유한다 (`SEEDS`/`ENEMIES`/`NPCS` 와 같은 방식).
표는 '몇 개인가' 만 안다. 회복량은 **고정값**이다 — 전투의 피해는 난수여야 리듬이
살지만 물약까지 흔들 이유가 없고, 고정이면 전투 밖에서 마실 때 난수원을 따로 만들
필요도 없다.

`Session` 은 가방을 들지 않는다. 필요할 때마다 DB 에서 읽는다 — 사본을 두면 진실이
둘이 되고, 읽는 곳(스냅샷·변경 직후)이 드물어 그 값을 치를 이유가 없다.

### 전리품은 피해를 준 사람 전원에게

```ts
rollDrops(enemy, contributions, rng): Award[]
```

순수 함수이고 난수는 주입된 시드 PRNG 다 — 같은 전투는 같은 전리품을 낸다.
막타를 넣은 사람만 받으면 실시간 0.5초 스윙에서 보상이 사실상 운으로 갈리고, 함께
싸울 이유가 줄어든다. 그래서 **각자 따로 판정**한다 (같이 잡으면 손해가 아니다).

`contributions` 는 `{playerId, damage}` 다. **`damage` 를 지금은 쓰지 않는다** —
그래도 인자로 받는 것은 '기여도에 비례한 차등 지급' 으로 가는 문을 열어 두기
위해서다. 그때 바뀌는 것은 이 함수의 몸통뿐이고 호출부도 표도 그대로다.

### 전투 중에는 '다음 스윙에' — 스킬과 한 자리를 나눠 쓴다

`Fighter` 의 큐는 하나다. 스킬이든 아이템이든 나중 입력이 앞의 것을 덮어쓰고,
발동하면 그 호흡의 기본 공격을 **대신한다**. 위협(어그로)도 올리지 않는다 —
회복 스킬이 그러지 않는 것과 같다. 교전 중이 아니면 기다릴 '다음 호흡' 이 없으므로
즉시 발동한다.

예약 '전에' 쓸 수 있는지 먼저 본다. 그러지 않으면 없는 물약을 예약해 두고 0.5초
뒤에야 "가지고 있지 않다" 를 듣는다 — 실시간에서 그건 거짓말에 가깝다.

와이어에는 `queuedSkill` / `queuedItem` 둘로 나뉘어 나가지만 **둘 다 채워지는 일은
없다** (한 자리에서 파생되기 때문이다).

### 테스트가 잡은 결함

소모가 두 문장이었다: `UPDATE ... WHERE qty > 1` 과 `DELETE ... WHERE qty = 1`.
둘 다 무조건 돌렸더니 `qty=2` 에서 UPDATE 가 1로 줄이고 곧바로 DELETE 가
'이제 1이니까' 지워서, **한 번 마셨는데 두 개가 사라졌다.** 지우기를 먼저 두고
`||` 로 이어 둘 중 하나만 돌게 고쳤다.

## 밸런스는 데이터, 씨앗은 코드
<!-- 아래 표의 '코드' 는 그 뒤 "지역 데이터를 JSON 으로" 에서 content/world/ 로
     옮겼다. 나누는 기준(고치는 비용)은 그대로다 — 형식만 JSON 이고 취급은
     코드와 같다. 그 절을 함께 볼 것. -->

```
content/balance/{player,enemies,skills,items}.json     ← 사람이 고치는 곳
server/content/balance.ts                              ← 읽고 검증한다 (zod)
server/engine/enemies.ts                               ← 타입(계약)만 있다
```

**나누는 기준은 "고치는 비용"이다.**

| | 고치면 | 어디에 |
|---|---|---|
| 수치 (HP·피해·쿨다운·드랍 확률·회복량) | 공짜. 되돌릴 수 있다 | **JSON** |
| 씨앗 (방 묘사 원본, 페르소나) | `seed_id` 가 바뀌어 **LLM 재생성** | 코드 취급 |
| 맵 구조, 적 배치 | 방이 생기거나 사라진다 | 코드 취급 |
| `sensitive_flags` | 그 방의 상태 수가 2배 (2^n) | 코드 취급 |
| 규칙 (치명타·어그로·큐) | — | 코드. 데이터로 쓰면 스크립트 언어가 된다 |

### `engine/` 은 파일을 읽지 않는다

`.eslintrc.cjs` 가 `engine/` → `node:fs` 와 `engine/` → `content/` 를 막는다
(일부러 어겨서 확인했다). 엔진은 결정론이어야 하고 I/O 를 모른다 — 시드 PRNG·
시계·렌더러와 똑같이 **주입**받는다.

```ts
resolvePlayerSwing(playerId, enemy, enemyHp, playerHp, playerMaxHp, skillId, rng, balance)
makeCombat(q, reg, emit, events, inventory, balance, clock, opts)
```

`server/content/` 도 경계가 있다: 파일을 읽어 계약으로 바꾸기만 하고 `db/`·
`net/`·`world/` 를 모른다. 조합은 언제나 `index.ts` 다.

### 정의와 배치는 다른 것이다

`enemies.json` 의 키가 곧 적 id 이고, **어느 방에 있는지는 거기 없다.**
배치는 맵 구조라서 지역 데이터(`content/world/regions/<id>.json` 의 `enemies`)가
소유하고, 같은 적을 여러 지역에 둘 수 있다 — `b2` 의 `rusted_watcher` 가 그
예다. 수치는 `enemies.json` 에 그대로 남고 한 줄도 바뀌지 않는다.

부팅에서 양방향으로 검증한다: 맵의 `'E'` 타일마다 배치가 있는가, 배치된 적이
정의에 있는가, 적이 켜는 플래그가 선언돼 있는가.

### 틀린 값이면 서버가 뜨지 않는다

zod 가 파일 안을 보고(`maxHp > 0`, `[최소, 최대]`, `chance ≤ 1`, 모르는 필드 거절),
로더와 시더가 파일을 넘나드는 참조를 본다(없는 아이템 드랍, 보스인데 리스폰,
배치된 적이 정의에 없음). **조용히 이상한 세계로 도는 것보다 부팅에서 죽는 편이
낫다.** 열 가지를 일부러 어겨 실제로 죽는 것을 확인했다.

`content/balance/README.md` 에 필드마다 무슨 뜻이고 왜 그 값인지 적어 두었다.

## 배포

배포 단위는 **항상 켜져 있는 프로세스 하나 + 디스크 하나**다.

```bash
npm run build          # dist/ (클라이언트)
npm run pregen         # 세계의 초기 문장을 미리 생성해 DB 에 박는다
npm start              # node --import tsx server/index.ts
```

### 서버리스에는 올릴 수 없다

Cloudflare Workers·Firebase Functions 는 **구조적으로** 맞지 않는다.

- **권위 상태가 메모리에 있다** — 세션 레지스트리, 0.5초 전투 틱, 리스폰 대기,
  유예 타이머, 승급 큐. 요청 단위로 뜨고 지는 런타임에서는 **인스턴스 두 개가
  곧 세계 두 개**다.
- `better-sqlite3` 는 네이티브 애드온이고, 휘발 인스턴스에는 디스크가 없다.
- 0.5초 틱과 ws 연결은 요청이 아니라 '계속 살아 있는 것' 이다.

맞는 곳은 볼륨 붙는 컨테이너다 (Fly.io / Railway / Render / VPS).
Cloudflare 라면 **Durable Objects** 가 개념상 정확히 맞지만 — 한 오브젝트가 한
세계를 소유하고, WebSocket 하이버네이션과 내장 SQLite 가 있다 — `db/` 전체와
부팅 경로를 다시 써야 한다. 지역이 여러 개가 되고 각각을 따로 굴리고 싶어질 때의
선택지다.

**이 이미지는 하나만 돌려야 한다.** 수평 확장은 지금 구조에서 정답이 아니다.

### 한 포트에서 정적 파일과 ws 를 함께

`ws` 를 별도 포트에 두면 세 가지가 한꺼번에 문제가 된다: HTTPS 페이지에서
`ws://` 가 **mixed content 로 차단**되고, 포트를 둘 열어야 하고, CORS 를 신경
써야 한다. 그래서 서버가 `dist/` 를 직접 서빙하고 같은 포트의 `/ws` 에서
업그레이드를 받는다. 클라이언트는 `location` 을 그대로 따라간다.

```ts
`${location.protocol === "https:" ? "wss:" : "ws:"}//${location.host}/ws`
```

개발에서는 vite 가 `/ws` 를 8787 로 프록시한다 — **분기가 클라이언트 코드에
없다.** 정적 서빙은 의존성 없이 `node:http` 로 했다 (`server/net/static.ts`).
`dist/` 밖은 나가지 않고(테스트가 경로 탈출 4종을 확인한다), 해시 박힌
`assets/` 만 영구 캐시하고 `index.html` 은 절대 캐시하지 않는다.

### 손봐야 했던 것들

| | |
|---|---|
| **IP 예산이 프록시 뒤에서 무너졌다** | `remoteAddress` 는 프록시 주소라 전원이 한 버킷이 된다. `MUD_TRUST_PROXY=n` 으로 `X-Forwarded-For` 의 **오른쪽에서 n번째**를 쓴다 (왼쪽은 클라이언트가 위조할 수 있다). 기본은 0 — 무조건 믿으면 예산이 통째로 우회된다 |
| **거절된 연결이 카운터를 영구 적립했다** | 상한 검사에서 `return` 한 뒤 아래에서 `close` 리스너를 달았다. 누적 거절이 상한에 닿으면 서버가 **모두를 영영 거부**하고 시도할 때마다 나빠졌다. 감소를 증가 직후에 등록한다 |
| **vite 가 `client/dist` 에 빌드했다** | `root: "client"` 라 기본 outDir 이 `client/dist` 인데 서버는 루트 `dist/` 를 본다. 빌드 로그의 `dist/index.html` 은 root 기준 상대경로라 눈으로는 안 보인다. `outDir: "../dist"` |
| **`npx` 로 띄우면 SIGTERM 이 안 닿는다** | 래퍼가 PID 1 이 되어 우아한 종료가 조용히 사라진다. `node --import tsx` 로 직접 띄운다 |

### 선생성 — 초기 문장은 운영 시작 전에 만든다

지연 생성은 방이 스무 개일 때의 이야기다. 방이 수백~수천 개면 "처음 들어간
사람이 만든다" 는 곧 "처음 들어간 방마다 누군가는 폴백을 본다" 이다.

`npm run pregen` 이 모든 방과 열린 주제를 미리 생성해 DB 에 박는다. 새 코드는
거의 없다 — 3단계가 플래그 변화 때 쓰는 그 경로를 모든 방에 한 번 돌릴 뿐이다.
**여러 번 돌려도 안전하다**: `ON CONFLICT DO NOTHING` 과 `WHERE source='fallback'`
이라 이미 확정된 문장은 건드리지 않는다. 지역을 하나 추가하고 다시 돌리면
그 지역만 생성된다.

폴백은 **없애지 않는다.** 선생성 뒤에는 (a) 플래그가 막 바뀌어 워커가 아직
못 따라잡은 순간, (b) 생성 실패 — 두 경우의 안전망이 된다. 규칙 4는 그대로이고
폴백이 드물어질 뿐이다.

한 가지 함정이 있었다: `events.pregenerate()` 는 이벤트 경로라 막히면 안 되므로
행 생성을 `await` 하지 않고 흘려보낸다. 도구가 그걸 그대로 쓰면 큐가 빈 순간에
`idle()` 이 즉시 돌아와 **폴백만 깔린 채 '성공' 으로 끝난다** (테스트가 잡았다:
19방 큐에 넣고 LLM 호출 0회). 도구는 행 생성을 기다린 뒤 승급을 건다.

### 환경변수

| | 기본 | |
|---|---|---|
| `MUD_PORT` | 8787 | 정적 + ws 를 함께 받는 포트 |
| `MUD_DB` | `mud.db` | SQLite 파일. 볼륨에 둔다 |
| `MUD_STATIC` | `dist` | 빌드된 클라이언트 |
| `MUD_TRUST_PROXY` | 0 | 신뢰하는 프록시 홉 수 |
| `MUD_MAX_SOCKETS` | 200 | 프로세스 전체 동시 접속 상한 |
| `MUD_NO_LLM` | — | `1` 이면 실물 모델 호출을 끈다 |
| `ANTHROPIC_API_KEY` | — | 없으면 결정론 폴백만 |

### 아직 안 된 것

- **`Dockerfile` 은 검증되지 않았다.** 이 환경에 도커 데몬이 없어 이미지를
  실제로 빌드해 보지 못했다. `npm run build` → `npm start` 경로와 SIGTERM 은
  실기로 확인했고, 이미지는 그 위에 얇게 얹은 것이다.
- **인증이 없다.** 무기명 토큰뿐이고 지금까지는 루프백이 사실상의 방어막이었다.
  공개하면 그게 사라진다. `MUD_MAX_SOCKETS` 가 최소한의 방어이고, 그 이상이
  필요하면 초대 코드가 가장 싸다.

## 지역 다중화

지역은 하나의 개념이 세 가지 일을 동시에 한다. 그게 이 단계의 요점이다.

| 지역이 정하는 것 | 왜 지역인가 |
|---|---|
| 관심영역 | `canSee` 가 지역 동일성이므로 지역 하나가 곧 팬아웃의 상한이다 |
| 서버측 안개 | 스냅샷이 '지금 있는 지역' 의 타일만 싣는다 |
| 진행 | 문이 플래그로 잠기므로 지역이 '얻는 것' 이 된다 |

방 50개짜리 지역 20개는 방 1000개짜리 지역 하나와 전혀 다른 물건이다.
후자면 반경 기반 `canSee`, 창(window) 미니맵, 스냅샷 분할이 **한꺼번에**
필요해진다. 전자는 셋 다 필요 없다 — 지역 경계가 이미 그 셋을 다 해준다.

### 문은 벽 자리에만 있다

`ExitDef` 는 `at`(어느 칸), `dir`(어느 방향), `to`(어디로), `requires`(어느
플래그가 켜져야), `oneWay` 로 이루어진다. 그 방향이 **벽이어야 한다**는 것을
부팅에서 검증한다. 걸어갈 수 있는 칸을 가리키면 같은 키 입력에 두 가지 뜻이
생긴다 — 한 칸 이동인가 지역 이동인가. 그 모호함은 판정 순서를 정해서
해결할 수 있는 종류가 아니라, 애초에 만들지 않는 편이 맞다.

덕분에 미니맵에는 문이 그려지지 않는다(문 자리는 `#` 다). 플레이어가 문의
존재를 아는 경로는 밀어 보고 듣는 문장 하나뿐이다.

### 와이어에서는 벽과 잠긴 문이 구별되지 않는다

`resolveMove` 는 `"wall"` 과 `"sealed"` 를 나눠서 돌려주지만, `ack.reason` 은
둘 다 `"blocked"` 다. 구별할 수 있으면 클라이언트가 모든 칸에서 사방으로
이동을 찔러 보는 것만으로 지도에 없는 문의 위치를 전부 알아낼 수 있다.
차이는 문장에만 있다:

```
단단한 벽이 앞을 막는다.
봉인된 문이다. 아직 열리지 않는다.
```

4b 의 "잠긴 주제는 목록에 아예 없다" 와 같은 규칙이다 — 감출 것은
클라이언트에 보내고 안 그리는 게 아니라, 보내지 않는다.

### 플래그를 엔진에 주입한다

문이 열렸는지는 DB 가 아는 사실이다. 엔진은 `db/` 를 import 하지 않으므로
`resolveMove(from, dir, isFlagOn)` 로 읽는 함수를 받는다 — 난수·시계·렌더러·
밸런스와 정확히 같은 방식이다. 주입 지점이 다섯 개가 됐지만 규칙은 하나다.

### 지역이 바뀔 때 스냅샷을 다시 보내지 않는다

새 격자는 `self.patch { region }` 로 간다. 스냅샷이 아닌 이유는 스냅샷에
**pending 큐를 비우는 부수효과**가 있기 때문이다 — 문을 지나는 순간 아직
응답이 안 온 액션들이 조용히 사라진다. 지역 이동은 그냥 이동이므로 그런 일이
있어서는 안 된다.

`SelfPatch` 주석은 "x/y 는 여기 절대 없다" 고 못박아 두었는데, 격자는 그
금지에 걸리지 않는다. 금지의 이유는 "늦게 도착한 패치가 이미 정산된 위치를
되감는다" 이고, 격자는 `pos.region` 의 함수라 순서가 뒤집혀도 같은 값으로
수렴한다.

방출 순서는 `ack` → `self.patch{region}` → `room.describe` 다. 뒤집히면 한
프레임 동안 옛 격자 위에 새 좌표가 찍혀 미니맵의 점이 벽 안에 박힌다.
그래도 미니맵은 `at.region === region.id` 를 한 번 더 본다 — 두 겹일 때만
방어다. 테스트가 이 순서를 직접 검사한다.

### 클라이언트 예측은 손대지 않았다

`Reconciler` 는 `step()` 으로만 예측하므로 문을 지나는 걸음을 예측하지
못한다. 고치지 않았다: 벽을 밀 때와 정확히 같은 상황이고, `ack` 가 **성공이든
거절이든 항상 권위 pos 를 싣기** 때문에 화면은 언제나
`replay(confirmed, pending)` 로 수렴한다. 롤백 분기가 없다는 성질이 여기서
한 번 더 값을 한다. 문을 알려면 클라이언트가 문의 목록을 받아야 하고,
그러면 위의 안개가 무너진다.

### 부팅 검증이 잡는 것

`assertWorldData` 가 지역마다 도는 것으로 바뀌었고, 문에 대한 조항이 붙었다.
전부 '오타 하나가 플레이어를 가두는' 종류다.

- 줄 길이가 제각각인 타일
- 씨앗 없는 걷는 칸 / **벽인 칸에 있는 씨앗**(영영 안 읽힌다)
- 선언되지 않은 플래그를 `sensitive` 에 적은 방
- `'E'` 타일과 적 배치의 양방향 불일치, 정의되지 않은 적 id
- 목적지 지역이 없는 문 / 목적지가 벽인 문 / 출발 칸이 벽인 문
- **걸을 수 있는 칸을 향한 문** (위의 모호함)
- 선언되지 않은 플래그로 잠근 문
- **왕복이라고 선언했는데 반대편에 짝이 없는 문** — 들어가면 못 나온다
- 벽 안의 `SPAWN`

`test/regions.ts` 는 이 조항들을 통과가 아니라 **위반으로** 검사한다. 데이터를
일부러 망가뜨려 `assertWorldData` 가 던지는지 보고, 되돌린 뒤 다시 통과하는지도
본다. 통과만 보면 검증기가 비어 있어도 초록불이라 아무것도 증명하지 못한다.

### 곁다리로 고친 것 — `seen` 쓰기

이동할 때마다 `seen` 배열 전체를 직렬화해 쓰고 있었다. 방 9개일 때는 안
보이지만 50방 × 20지역이면 걸음마다 1000개짜리 JSON 이다. `commitMove`(seen
없음)와 `commitMoveSeen` 으로 나눴다 — 안개가 넓어지는 순간에만 쓴다.

### 두 번째 지역이 실제로 있다

`b2` "봉인된 서고" 8방. `b1` (5,5) 의 봉인된 문이 `guardian_slain` 으로
열린다 — 4a(전투) → 3단계(플래그) → 4b(제단지기의 `sealed_door` 주제) 로
이어지던 고리가 여기서 한 번 더 이어져, 파수꾼을 쓰러뜨리는 것이 처음으로
**장소**를 준다.

`b1` 의 타일·씨앗·`sensitive` 는 한 글자도 건드리지 않았다. `seedId` 가 내용
파생이므로 한 글자만 바꿔도 이미 생성된 텍스트가 전부 캐시 미스가 된다.

`b2` 에는 `rusted_watcher` 를 다시 배치했다. `content/balance/enemies.json` 은
한 줄도 바뀌지 않는다 — "정의는 밸런스, 배치는 맵" 이 실제로 값을 하는 첫
지점이다.

## 지역 데이터를 JSON 으로

저작 파이프라인의 앞 절반. 도구가 무언가를 '써낼' 곳이 있어야 하고, 그곳은
소스 코드가 아니라 데이터여야 한다.

```
content/world/world.json          스폰
content/world/regions/<id>.json   지역 하나. 파일 이름이 곧 id 다
server/content/world.ts           읽고 검증한다 (zod)
server/engine/map.ts              makeMap(data) -> GameMap. 데이터는 없다
```

밸런스와 정확히 같은 모양이다. **다른 점은 하나**: 수치는 바꿔도 공짜지만
씨앗은 아니다. 한 글자만 고쳐도 `seed_id` 가 바뀌어 그 방의 생성된 텍스트가
전부 캐시 미스가 된다. 그래서 형식만 JSON 이고 **취급은 코드와 같다** —
고칠 때는 리뷰를 거친다.

### 주입 지점이 하나 더 늘었다

```ts
new World(map)
resolveMove(map, from, dir, isFlagOn)
makePresence(reg, emit, map, ...)
makeCombat(q, reg, emit, events, inventory, map, balance, clock, opts)
seed(db, q, map, balance, now)
```

모듈 전역에 두고 `setRegions()` 로 밀어넣지 않았다. 그러면 '아직 안 채워진 맵'
이라는 상태가 생기고, 테스트가 서로의 세계를 덮어쓴다.

### 씨앗은 한 글자도 바뀌지 않았다

형식을 옮기는 작업에서 가장 조용히 일어날 수 있는 사고가 그것이다. 옮기기 전
코드에서 27방의 `seedId` 와 `flagsDeclHash` 를 전부 뽑아 옮긴 뒤와 비교했고
전부 동일하다. `test/world.ts` 가 그중 다섯 개를 표로 박아 회귀를 막는다 —
**갱신하는 표가 아니라, 어긋나면 씨앗을 되돌리는 표다.**

`content_hash` 는 한 번 바뀐다. 옛 코드가 해시 preimage 의 구분자를 자리마다
다르게 쓰고 있었고(어떤 곳은 빈 문자열, 어떤 곳은 예전 편집에서 섞여 들어간
제어문자), 이번에 하나로 통일했다. 구분자 없이 이어 붙이면 `["ab","c"]` 와
`["a","bc"]` 가 같은 preimage 가 된다. 값이 바뀌면 시더가 단축경로를 한 번
건너뛰고 `rooms`/`npcs` 를 다시 upsert 할 뿐이다 — UPSERT 라 멱등하고,
`room_text` 는 `state_hash` 로 키가 잡히므로 텍스트는 한 줄도 안 건드려진다.

### 주입 테스트가 결함을 하나 잡았다

"다른 세계를 넘기면 그 세계로 도는가"를 검사하려고 두 방짜리 세계를 넣었더니
부팅이 `FOREIGN KEY constraint failed` 로 죽었다. NPC 는 아직 코드에 있고
(`engine/npcs.ts`) 제단지기가 `"b1:3,1"` 을 가리키는데, 그 방이 없었다.
어느 NPC 가 어느 방을 못 찾았는지는 그 메시지 어디에도 없다.
`assertWorldData` 에 조항을 넣었다.

## 내용 저작 파이프라인

지역이 스무 개면 방이 천 개다. 씨앗을 손으로 쓸 수 없다.

```
npm run author -- b3 --dry-run    # 지도만 그려 본다. 모델을 부르지 않는다
npm run author -- b3              # 개요 + 씨앗을 만들어 regions/b3.json 에 쓴다
```

### 저작 시점의 LLM 은 규칙 1·2와 부딪히지 않는다

규칙 1·2는 **런타임**의 규칙이다 — 모델 출력이 살아 있는 게임 상태를 바꾸는
경로가 없어야 한다는 것. 저작에서 나온 문장은 파일로 나가 사람의 리뷰를 거쳐
커밋되고, 그때부터는 코드와 똑같이 취급된다 (규칙 3: 씨앗은 불변).

이 구분을 주석이 아니라 린트로 못박았다. `server/index.ts`, `net/`, `world/`,
`db/` 가 `narration/author` 를 import 하면 빌드 에러다. 런타임에는 그 경로가
아예 존재하지 않는다.

### 분업 — 배치는 코드, 문장은 모델

| | 누가 |
|---|---|
| 배치 (타일) | 결정론적 생성기 `server/engine/layout.ts` |
| 씨앗 (문장) | LLM `server/narration/author.ts` |
| 적·문·`sensitive` | 사람 |
| 검토·커밋 | 사람 |

**배치를 모델에게 맡기지 않는 이유**는 취향이 아니다. 맵 구조는 세계의 진실이고
(규칙 1), 모델이 만들면 연결성도, 출구가 벽 자리라는 성질도, `'E'` 타일과 적
배치의 짝도 아무것도 보장되지 않는다. 대신 프론티어 굴착 생성기를 쓴다: 이미
뚫린 칸에 붙은 벽 칸만 뚫으므로 **결과가 항상 연결되어 있다.** 연결성을 나중에
검사해 고치는 것이 아니라 만들어질 수 없게 한 것이다. 뚫린 이웃이 1개 이하일
때만 뚫어 통로를 만들고, 가끔(`loopChance`) 2개까지 허용해 고리를 낸다 —
완전한 나무 미로는 막다른 길이 너무 많아 걷기 지루하다.

시드가 브리프에 적혀 있으므로 **지도가 어디서 왔는지가 커밋 안에 남는다.**

### 개요 1회 + 열 칸씩

방마다 따로 물으면 서로를 모르는 50개의 문장이 나온다. 지역 전체를 한 응답으로
받으면 잘린다. 그래서 먼저 지역 '개요'를 한 번 만들어 브리프에 적어 두고,
그걸 문맥에 얹어 열 칸씩 묶어 묻는다. 지역당 6회쯤.

개요는 한 번 만들면 다시 만들지 않는다 — 방을 나중에 더 뚫어도 같은 장소로
이어져야 한다. 묶음마다 파일에 쓰므로 중간에 죽어도 이어서 돌리면 된다.

각 칸에는 **이웃 정보를 함께 준다** (`"북·동 (갈림길)"`). 안 주면 모델이 지도에
없는 문과 계단을 만들어낸다.

### 모델은 세계를 만들 수 없다

`narration/author.ts` 에서 가장 중요한 열 줄은 이것이다:

```ts
const wanted = new Set(asks.map((a) => a.coord));
for (const [k, v] of Object.entries(raw)) {
  if (!wanted.has(k)) continue;
  ...
}
```

모델이 돌려준 것 중 **우리가 물어본 좌표만** 통과시킨다. 물어보지 않은 좌표를
그냥 받으면 모델이 방을 만들어내는 것과 같아진다 — 지도에 없는 칸에 씨앗이
생기고, 그 씨앗이 다음 사람에게는 '원래 있던 방'으로 보인다.

빠진 좌표는 **채우지 않는다.** 조용한 폴백은 "특징 없는 돌 통로" 50개를
커밋하게 만든다. 도구가 "아직 비어 있는 칸 3" 이라고 말하고, 다시 돌리면 그
칸만 다시 짓는다.

### 덮어쓰지 않는다 (규칙 3)

도구는 **빈 것만 채운다.** 씨앗도, 타일도, 개요도, 사람이 붙인 적·문도.

씨앗 한 글자가 바뀌면 `seed_id` 가 바뀌어 그 방의 생성된 텍스트가 전부 캐시
미스가 된다. 타일을 다시 만들면 좌표가 통째로 밀려서 **이미 쓴 씨앗이 전혀 다른
방에 붙는다** — 조용히 세계가 뒤섞인다.

다시 짓고 싶으면 사람이 그 줄을 지우고 도구를 다시 돌린다. 지우는 것은 사람의
결정이어야 한다.

### 테스트가 그 두 가지를 위반으로 검사한다

`test/author.ts` 45검사. 통과만 보면 문지기가 비어 있어도 초록불이라
아무것도 증명하지 못하므로, 일부러 위반하는 가짜 저자를 꽂는다:

- 물어보지 않은 좌표(`"99,99"`)·벽인 칸(`"0,0"`)·빈 문자열·숫자를 섞어 돌려준다
- 사람이 손으로 고친 씨앗을 두고 도구를 다시 돌린다
- 끊긴 격자를 브리프에 적는다
- 응답이 `max_tokens` 에 잘린다

그리고 코드를 일부러 망가뜨려(문지기 한 줄을 주석 처리, 덮어쓰기 허용) 검사가
실제로 빨강이 되는 것을 확인했다 — 각각 1개·5개가 떨어진다.

마지막으로 만들어진 지역을 그대로 `loadWorld` → `assertWorldData` 에 넣어,
**사람이 손볼 것 없이 부팅 검증을 통과하는지** 본다.

## NPC 도 지역 파일로

남아 있던 마지막 코드↔데이터 결합. `server/engine/npcs.ts` 가 NPC 목록을
들고 있었고, 제단지기가 `roomId: "b1:3,1"` 을 문자열로 가리켰다.

**전역 목록의 문제는 그 문자열이다.** 지역과 어긋나도 아무도 모른다 —
지역 데이터를 JSON 으로 옮길 때 두 방짜리 세계를 주입해 봤더니 부팅이
`FOREIGN KEY constraint failed` 로 죽었고, 그 메시지에는 어느 NPC 가 어느
방을 못 찾았는지가 없었다.

이제 NPC 는 **자기가 서 있는 지역의 파일 안에** 있고 좌표만 적는다:

```json
"npcs": {
  "altar_keeper": {
    "at": "3,1",
    "name": "제단지기",
    "persona": "...",
    "sensitive": ["guardian_slain"],
    "topics": [ { "id": "greet", "label": null, "seed": "...", "requires": null }, ... ]
  }
}
```

어느 지역인지는 **어느 파일에 있는가**가 말해 주고, 방은 좌표가 말해 준다.
`roomId` 를 사람이 손으로 적는 자리는 이제 없다 — `makeMap` 이 부팅에서 한 번
조립한다. 어긋날 수 있는 것은 "그 좌표가 이 지역의 걷는 칸인가" 하나로 줄었고,
그건 같은 파일을 보는 검증기가 바로 안다.

### `topics` 만 배열이다

이 저장소에서 **키가 곧 id** 라는 규칙의 유일한 예외다. 주제의 순서가 곧 대화
메뉴의 순서라서, 순서를 JSON 객체의 키 순서에 맡기고 싶지 않았다.

### 남은 것 / 간 것

`engine/npcs.ts` 에는 이제 **규칙만** 있다: 타입, `GREET`, `topicOf`,
그리고 `npcSeedId`. 마지막 것에 주석을 하나 붙였다 —

```ts
export const npcSeedId = (npc: Pick<NpcDef, "persona">, topic: TopicDef): string =>
  sha(`${npc.persona}\n${topic.seed}`, 8);
```

**여기에 id 도 방도 들어가지 않는다.** NPC 를 다른 방으로 옮기거나 이름을
바꿔도 이미 만든 대사는 그대로다 — 대사는 '누가 어디 있는가'가 아니라
'무엇을 어떤 목소리로 아는가'의 함수이기 때문이다.

### 대사도 한 글자 안 바뀌었다

방 씨앗 때와 같은 방식으로 확인했다. 옮기기 전 코드에서 네 주제의
`npcSeedId` 를 뽑아 옮긴 뒤와 비교했고 전부 동일하다
(`4128f090` / `3b499c52` / `c9861dd3` / `91ffd8be`). `test/world.ts` 가
그 표를 박아 두고 주제 순서까지 함께 본다.

### 부팅 검증이 늘었다

로더가 보는 것 (한 파일 안): NPC id 형식(`:` 금지 — 승급 큐 키의 구분자),
같은 지역 안의 주제 id 중복, 모르는 필드.
로더가 보는 것 (파일을 넘나들어): **NPC id 의 전역 유일성** — 지역마다 파일이
나뉘어 있으므로 이건 여기서만 볼 수 있다.
`assertWorldData` 가 보는 것: NPC 가 걷는 칸에 서 있는가, `sensitive` 와
주제의 `requires` 가 선언된 플래그인가.

`test/regions.ts` 는 이걸 통과가 아니라 **위반으로** 검사한다 — NPC 를 벽에
세우고, 없는 플래그에 반응하게 하고, 없는 플래그로 주제를 열어 본다.

### 그래서 주입 테스트가 정직해졌다

전에는 "다른 세계를 넘기면 그 세계로 도는가"를 검사하면서도 그 세계에
`b1` 과 `b1:3,1` 이 있어야 했다. 이제 **NPC 가 하나도 없는 두 방짜리 세계**로
부팅된다. 코드가 세계를 들고 있지 않다는 것이 이제 진짜로 검사된다.

## 세계관을 갈아끼운다 — 그리고 검사가 280곳 깨졌다

첫 세계(지하 서고)를 버리고, 사용자가 따로 만든 세계관 마인드맵(WorldMind)의
설정으로 세계를 다시 지었다. 근미래 지구, 도시 한가운데의 공동화, 그 안의
'괴담' 들, 그리고 5년 전 흔적도 없이 사라진 극비 연구소.

지역 3개 · 방 50개 · NPC 1 · 플래그 2. 전부 `--layout-only` 로 타일만 뽑고
씨앗은 손으로 썼다 (모델 호출 0회).

```
d6town  대공동 6구역          40방  마을·스폰. NPC 6명
d6      대공동 6구역 진입로   10방  마을 ↔ 괴담. 괴담 소품 받침대
ue001   [UE-001] 광기의 연구실 28방  기록실의 괴령 · 관측자(NPC)
ue001b  [UE-001] 격리 구역     12방  journal_recovered 로 잠긴 문 너머. 증식체
```

인물의 자리는 마인드맵이 이미 정해 두고 있었다 — 세실은 "6구역 술집 구석",
이졸데는 "6구역 성소 응접실", 리넷타는 "6교구 어딘가". 지어낸 것이 아니라
읽어서 옮긴 것이다.

### 콘텐츠가 검사를 깨뜨렸다 — 그게 진짜 문제였다

세계를 갈아끼우자 테스트 280곳이 한꺼번에 빨개졌다. 프로토콜·전투·인벤토리·
UI 검사가 **좌표와 문장을 운영 데이터에서 읽고 있었기 때문이다.** 방 하나를
옮기는 일이 무관한 검사 백 개를 깨뜨리는 구조였다.

고친 방향은 콘텐츠에 맞춰 검사를 다시 쓰는 것이 **아니라**, 검사가 자기
세계를 갖게 하는 것이다. 자리는 이미 있었다 — `BootOptions.world` 는 "다른
세계를 넘기면 그 세계로 도는가" 를 검사하려고 만들어 둔 것이었는데, 그게
그대로 답이었다.

`test/fixture.ts` 가 옛 세계(지하 서고)를 통째로 들고 있다. 좌표도 씨앗
문자열도 그대로라서, 검사 대부분은 `boot(DB, PORT, { ...FIXTURE })` 한 줄만
붙이고 손대지 않았다.

같은 이유로 **밸런스와 mood 도 주입**이 됐다:

```ts
boot(DB, PORT, { world: FIXTURE_WORLD, balance: FIXTURE_BALANCE, moods: FIXTURE_MOODS })
```

운영 콘텐츠 자체를 보는 넷만 실제 데이터를 읽는다 — `world`(씨앗이 안
바뀌었는가), `regions`(지역 데이터 정합성), `balance`(밸런스 파일),
`author`(저작 도구).

### 코드에 남아 있던 프로즈

폴백 꼬리가 `static.ts` 에 상수로 박혀 있었다:

```ts
const TAIL = "발소리가 축축한 벽에 둔하게 부딪힌다.";
```

근미래 연구소에서 "축축한 벽" 이 나왔다. 세계관을 바꿔 봐야 드러나는 종류의
결함이다. `prompts/tails.ko.md` 로 옮기고 **씨앗의 해시로 고르게** 했다 —
하나면 방 50개가 전부 같은 문장으로 끝난다. 방마다 고정이고 같은 방은 언제나
같은 꼬리다(폴백도 캐시에 기록되므로 굴릴 때마다 달라지면 안 된다).

`CLAUDE.md` 에 규칙으로 올렸다: **플레이어가 읽는 문장은 코드에 두지 않는다.**

### 폴백만으로도 읽을 만하다

이게 이번에 확인된 가장 쓸모 있는 사실이다. 폴백은 `${씨앗}. ${꼬리}` 이고,
씨앗을 문장으로 제대로 쓰면 결과가 그대로 게임 텍스트가 된다:

```
6구역의 가장자리. 이계에서 흘러든 것들이 말없이 지나다닌다. 조명이 아주 잠깐 흔들렸다가 돌아온다.
괴담의 입구. 있을 리 없는 자동문이 소리 없이 닫힌다. 발소리가 생각보다 늦게 되돌아온다.
관측창이 늘어선 복도. 유리마다 안쪽에서 손자국이 눌려 있다. 숨을 쉴 때마다 목 안쪽이 서늘하다.
```

즉 **LLM 은 필수가 아니라 승급이다.** API 키 없이 출시할 수 있고, 나중에 키를
넣고 `npm run pregen` 을 돌리면 `WHERE source='fallback'` 인 행만 조용히
갈아끼워진다.

### 마인드맵 → 엔진

| WorldMind | oldrpg |
|---|---|
| 괴담 하나 (`[UE-001] 광기의 연구실`) | 지역 |
| 괴담의 진행 | `world_flags` + 문의 `requires` |
| 괴이 — 괴물(육신 있음)/괴령(육신 없음) | `enemies.json` |
| 어둠 에너지 · 기물 | `items.json` |
| **태고의 어둠 — 괴담의 '게임 마스터'** | `moods/*.md` 의 `near`/`far` 화자 |

마지막 줄이 특히 잘 맞았다. 플래그가 켜지는 순간 나가는 문장이 원래는 상황
묘사였는데, 이 세계에서는 **괴담의 주최자가 알아차렸다는 신호**가 된다.

## 다음

로드맵은 끝났다. 여기서부터는 순서가 정해져 있지 않다.

- **전투 요약을 LLM 으로**: 전투가 끝난 뒤 한 문단. 실시간 제약 밖이라
  2단계 파이프라인을 그대로 쓴다.
- **실제로 지역을 스무 개 만들기**: 도구는 있다. 남은 것은 `theme` 을 쓰는 일과
  API 키다. 저작 도구는 아직 NPC 를 만들지 않는다 — 누가 어디 서서 무엇을
  아는가는 진행의 결정이라 사람이 쓴다. 필요해지면 씨앗과 같은 방식으로
  붙일 수 있다 (지역 파일 안에 있으므로 도구가 쓸 자리는 이미 있다).
- **진짜 인증**: 공개하면 무기명 토큰만으로는 부족하다. `players.account_id` +
  `accounts` 가 붙고 `token_hash` 가 그리 옮겨간다.
